# 工作循环：音色方案先过门，PL 完成最终实现（2026-10-21 修订）

本文件保留原文件名以免历史链接失效。现行顺序由用户确认：先找到可接受的软件音色转换方案，再做 PL 资源评估、部署验证和实时加速。PL 是项目最终重点，但不能提前硬化尚未通过音色门槛的算法。

## 强制循环

1. 远端无板卡协作者开发 PS/电脑端候选，提交代码、复现命令、客观指标和失败样例。
2. 候选同时通过身份、P10、源泄漏、UTMOS 和 CER 门槛后，交本地试听。
3. 本地确认音色可接受后，评估定点误差、参数量、MAC、缓存、带宽和 Zynq-7020 PL 资源。
4. 部署到 PL 并验证音色。若音色下降，先在 PL 表示、定点和结构上修复；多轮仍无法恢复才回到第 1 步换方案。
5. 音色在 PL 上保持后，再优化流水线、并行度、DMA 和缓存，满足实时性。

未通过第 2 步的候选不得进入 PL 实现。预先完成的 Vivado 2026.1 重建、资源账本和音频链验证只作为基础设施，不代表某个音色算法已获准硬化。

## 协作与证据

所有任务状态写入根目录 `coummucation.md`。每完成一轮方案或一轮测试，必须提交并推送 GitHub；失败轮次也提交，保留复现命令、原始指标、结论和下一步。
