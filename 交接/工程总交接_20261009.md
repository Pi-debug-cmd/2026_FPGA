## 2. 板上资源分工及真实数据流

硬件：野火 ZYNQ7020/7020 板，Zynq-7000 双 Cortex-A9（实测两核均约 666667 kHz），PS 侧 Linux、DDR、ALSA 音频驱动、串口和 GEMM 用户态/驱动接口；PL 侧包含 I2S 接收/发送、audio formatter/DMA、动态音频时钟及 int8 矩阵乘加 IP。音频 codec 是 WM8960；其模拟麦克风/耳机音量由 ALSA mixer 设置，I2C 由 PS EMIO 经 PL IOBUF 到板外引脚；音频/GEMM 中断合并接入 PS GIC。GEMM 的 weights/input/output 三个主口分别走独立互连到 PS HP1/HP2/HP3，以 DDR 交换数据。**PL 目前不是完整神经网络；它只加速 16 类/个被导出的 int8 矩阵运算。卷积、非线性、attention 整理、量化/反量化、流控等大量工作仍在 PS CPU。** PC GPU 只用于训练和离线审核，比赛演示时的转换不应依赖 PC 计算。

实际实时链：麦克风模拟声 → WM8960 ADC → I2S/PL audio formatter/DMA → Linux ALSA hw:0,1 以 32 kHz、S24_LE、双声道采集 → audio_bridge32 down，二点平均降到 16 kHz 浮点单声道 → deploy_kv_fused 的流式 LLVC 缩减学生模型按每块 208 采样（13 ms）处理、双 A9 前后段流水，并经 GEMM 驱动让 PL 计算 16 个 int8 矩阵 → audio_bridge32 up，线性插值回 32 kHz、S24_LE 双声道 → ALSA hw:0,0 → PL/I2S → WM8960 DAC → 音箱。运行脚本启 5 个长期进程：capture、down、convert、up、playback，FIFO 在 /run/kvf-native32，日志在同目录。模型权重不藏在 FPGA 位流里，而是板上 /home/root/llvc_reduced_20261008/model.bin。

当前恢复的缓冲：采集 period/buffer=2048/8192，播放=2048/32768，起播预填 500 ms。这本身贡献明显延迟；缩至 1024/4096、1024/8192 和 150 ms 后此前很快积累录放异常，已回退。当前长期运行同样已积累 483/396 次异常，说明计算/调度/缓冲尚未解决。音频桥的简单二点平均和线性插值是音质风险点，需独立评估。板端模型每 13 ms 块的双段平均时间约 12.7/12.7 ms，几乎无算力余量，偶发超过块预算就可能断流。优化时不能只靠缩小缓冲。

## 3. 已建立的基础、证据边界

A：官方位流下 arecord 1 秒得到 64000 字节，aplay 返回 0 并约 1.047 秒自行退出；采集 peak≈0.748、rms≈0.112。**只差物理断电重启后官方配置可恢复的正式证据**。用户可在不影响其他试验时完成，但别为了补 A 而打断正在运行的转换。A 原始日志在 核心材料/验收记录/A_基线。

B：自定义 PL 位流下录放与 GEMM 共存，三项硬标准通过。arecord/aplay 复测与 A 基线一致；16 个 GEMM 矩阵用当前源码重新交叉编译的 check_gemm_clean 全部 0 错；Vivado WNS=+0.141 ns、WHS=+0.049 ns、TNS/THS=0，Bitgen 完成。四个修复根因：中断未接 GIC、GEMM 三主口共用互连导致地址重叠、PS EMIO I2C 未经 IOBUF 外引、wrapper 重复引用。板上预置的旧 check_gemm 是过期二进制，会假报 matrix6 错，不能拿它推翻新源码和独立复核。完整证据 核心材料/验收记录/B_PL音频/B关验收记录_20261008.md 和 55/67/69/70 日志。**B 仅是 PL 音频与 GEMM 数值共存，不是声音转换验收。**

C：现有 v2 模型 16 个 int8 GEMM 数值正确；7020 PS+PL 整段 69120 采样输出对 PC int8 参考 corr=0.999957949、RMSE=0.000431711。短输入边界返回码/长度已检；正确 DMA ko 替换旧模块前后整段输出 SHA 完全相同。逐层旧 JSON 的 d2e 钩子节点不一致，不能宣称“逐层全部通过”；终端波形等价已通过。过期 out_pc_red.bin 和旧“C输出.wav”曾导致错误的声纹结论，已重命名标注；当前对照 PC int8 约 0.6904、PyTorch 流式约 0.6938，流式切块本身不是巨大音色差距的主因。完整说明 核心材料/验收记录/C_数值/C_D_接续记录_20261009.md。

D（持续低延迟）与音色质量：未通过。K/V GEMM 融合使离线 5 秒输入约 4.95 秒、与原版输出逐位相同；40 秒实流时间戳当时只差约 40 ms 采样进度，120 秒一度未明显积压，但有短断流，处理余量极薄。**最新长时间只读状况累计 overrun 483、underrun 396，表明“长期稳定、低延迟”依然不成立。**用户真人听感明确否定现有音色及延迟。缩短 ALSA 缓冲、启用 SCHED_FIFO、inconv4 和 outconv multiacc 的既往尝试未成为可接受替代：或异常增多、或性能反退、或输出变更。详见 C_数值/52、69、70、73、85、86、87、88 和 C_D_接续记录。

## 4. 模型、训练、离线审核：哪些结论可信

## 6. 接手后的执行顺序与通过标准

1. 阅读本文件、文件校验清单.json、B 验收记录、C_D 接续记录和 88_handoff_readonly_status.log；确认文件存在、SHA 对得上。新 PC 先恢复路径和 Python/Vivado/SDK 环境。板已断电就先恢复 B 位流与正确 ko；仍在运行就只读核状态，不为例行检查反复打断用户音频。
2. 先把“当前主版本”锁住：model.bin、已验 deploy_kv_fused、500 ms 脚本、正确 PL 位流及 ko 均不得被候选覆盖。将新模型、程序和测试 WAV 放独立目录并记录 SHA；失败可立即回到旧二进制/模型。
3. 用 torch 环境导出 bias_content_v1；检查 112 号偏置数组确有 384 个 float、版本 v3，所有 16 个 int8 矩阵参数布局未意外改。用固定中文和至少四段留出源语音验证 C/PC int8 与 PyTorch 音频高相关、低误差，另看各段响度和边界。若失败，修数值而不安排试听。
4. 在未连接真实麦克风的短音频离线测试中，确认板上程序和 PL 正确、无 crash、输出长度与输入相等；5 秒与更长时长计时，前后两线程均有实质余量，不能仅平均 12.7 ms 略小于 13 ms 就宣布长期实时。尤其要核查 overrun/underrun 随时间增长。候选若明显拖慢，不切进实流。
