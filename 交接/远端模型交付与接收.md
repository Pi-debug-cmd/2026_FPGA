# 远端音色模型交付与接收（Remote-PS-C / GPT+Codex 必读）

本文件是给另一台电脑上的 Remote-PS-C / GPT+Codex 的操作要求，也是板卡方接收模型的验收清单。GPT 与 Codex 是同一位远端合作者的两个工具入口，共用一个 GitHub 身份、任务分支和 `CLAIMED` 记录。**目标不是只上传训练代码，而是使有本私有仓库权限的接收者能从 GitHub 取回完整模型、校验并实际运行。**协作者拥有仓库写权限，不会使其电脑上的本地权重自动进入 GitHub；模型文件仍须单独上传。

## 远端电脑的存储边界（下载前先执行）

- 先查看另一台电脑各**本地固定盘**的剩余空间，估算仓库、音频、第三方权重、Python 环境、训练检查点、缓存、临时文件和 Release 打包所需总量，并留有余量。优先选空间充足的**非系统盘**；不要假设一定有 `D:`，也不要默认把大型内容放到 `C:`。空间不够时先向操作者说明所需容量和候选盘位，再开始下载或训练。
- 在选中的盘建立**一个项目总目录**（例如 `E:\2026_FPGA_workspace`，盘符只是示例）。仓库检出、虚拟环境、数据/下载、第三方模型、训练输出、缓存、临时文件、日志、干净目录复验、Release 待上传包，都放在这个总目录的子目录中。不要把模型或依赖散放到桌面、下载文件夹、用户主目录、其他盘符或全局 Python 环境；不要为了腾空间自行删除或移动操作者的已有文件。
- Windows 可先用 `Get-CimInstance Win32_LogicalDisk -Filter 'DriveType=3'` 查看本地固定盘容量和剩余空间；选盘后记录盘符与开始时剩余容量。每轮大量下载/训练后核查新生成的大文件是否仍在项目总目录、系统盘剩余空间是否异常下降；发现大缓存跑到目录外时先停止并修正路径，再继续生成。
- 在启动大量下载、包安装、训练和推理之前，设置**该任务进程**的 `TEMP`、`TMP`、`PIP_CACHE_DIR`、`HF_HOME`、`TORCH_HOME`、`XDG_CACHE_HOME` 等缓存/临时路径到项目总目录；使用其他框架时核对它的缓存和检查点参数。虚拟环境也在总目录内创建。以下是 PowerShell 示例；先把第一行改成实际选中的非系统盘，且在同一会话中启动后续程序：

```powershell
$workspaceRoot = 'E:\2026_FPGA_workspace' # 示例：先核对并改为实际空间充足的盘
@('repo','venv','data','models','runs','release','cache','tmp','receive-check') | ForEach-Object {
    New-Item -ItemType Directory -Force -Path (Join-Path $workspaceRoot $_) | Out-Null
}
$env:TEMP = Join-Path $workspaceRoot 'tmp'
$env:TMP = $env:TEMP
$env:PIP_CACHE_DIR = Join-Path $workspaceRoot 'cache\pip'
$env:HF_HOME = Join-Path $workspaceRoot 'cache\huggingface'
$env:TORCH_HOME = Join-Path $workspaceRoot 'cache\torch'
$env:XDG_CACHE_HOME = Join-Path $workspaceRoot 'cache\xdg'
$env:UV_CACHE_DIR = Join-Path $workspaceRoot 'cache\uv'
```

- 先确认这些设置在实际训练/推理进程中生效，再安装依赖或下载模型；如果使用 Conda、CUDA、浏览器下载器或其他有独立缓存的软件，同样把其**大文件路径**显式设在总目录。记录所选根目录、下载体积、运行过程中最大占用和无法重定向的例外。系统、GitHub CLI、GPT 客户端或 Codex 可能仍在用户配置目录写入少量凭据/设置；不要声称能绝对零写入 `C:`，也不要复制凭据到模型包。

2. 盘点仓库文件树，按本轮任务阅读相关的 `src/`、`build/`、`sim/`、`report/`、`board/`、`team_project/`、`人物音频资料/` 与 `板载资料/`；尤其核对 `report/fallback_one_to_one_assets_20261021.json`、`board/hardware_inventory.md`、`板载资料/说明.md` 和其中指向的原理图/硬件规格。`team_project/development_plan.md`、早期 G1～G7 和旧交接为历史记录；冲突时以 `plan.md`、`AGENTS.md` 和较新的正式证据为准。无需逐字读取每个历史日志或音频二进制，但必须确认直接依赖的资产、版本和 SHA-256，不能把本机不存在的 `build/generated/` 或第三方权重当作已提供。
3. 当前只开放 `PS-20261021-10`：固定一名男性输入者到既定女性目标的一对一质量上限。固定男声录音 1～3 训练、4 验证、5 锁定验收；目标女声 Track 5～8 建模、Track 9 锁定留出。必须遵守 `plan.md` 的防泄漏规则。此级完成前不得声称陌生多人或现场注册目标已通过。
4. 远端电脑无板卡/Vivado，能做训练、离线评测、因果压缩和 Cortex-A9 资源预算；不能把电脑试听、模拟运行或估算写成 7020 板上结果。缺少必需资料或 GitHub 权限时，在 `coummucation.md` 精确列出缺项和恢复条件，标记 `BLOCKED`，不要用占位文件替代。

## 每轮代码与模型分别交付

**代码和证据放任务分支/PR：**训练、导出、推理、评测、依赖版本、配置、数据切分与复现命令进入 Git；客观报告进入 `report/`，并更新 `coummucation.md`。提交失败实验也要如实记录。不得把新真人语音、生成语音或模型权重强制加入 Git。

**可执行模型放本私有仓库的 GitHub Release 附件：**当一个候选要交给板卡方复现、试听或继续优化时，打包该候选的**全部推理必需文件**，包括但不限于编码器/转换器/声码器权重、目标条件、归一化统计、词表或码本、网络结构与音频预处理配置、运行说明。若依赖第三方权重，可随包交付，或记录官方下载位置、精确版本、SHA-256 和自动获取步骤；接收者不得靠猜文件名或沿用 Claude 电脑的缓存。训练数据和历史实验缓存不用混入推理包。目标人物原始 WAV 仅使用仓库已获准共享的素材；新真人录音另按 `AGENTS.md` 授权。

给模型包使用唯一 Release 标签，例如与任务编号和候选版本绑定；标签指向包含该候选推理代码的确切提交。上传后用 `gh release view` 核对仓库、标签、附件名和字节数。`gh release create` 未指定 `--target` 时可能把新标签指向默认分支，因此必须显式指定候选提交或先验证标签指向。PR 可以先存在；Release 和 PR 均需有仓库权限的人可访问。不要把草稿 Release、仅本地路径或 PR 附件说成已交付。

Remote-PS-C / GPT+Codex 在自己的电脑上完成打包、提交和推送后，可按下列结构发布（将标签、包路径和说明文件替换为本轮真实值；包文件不加入 Git）：

```powershell
$workspaceRoot = 'E:\2026_FPGA_workspace' # 改为前述实际选定的总目录
$repo = 'Pi-debug-cmd/2026_FPGA'
$tag = 'model-PS-20261021-10-v1'
$sourceCommit = (git rev-parse HEAD).Trim()
$bundle = Join-Path $workspaceRoot 'release\model_bundle.zip'
$releaseNotes = Join-Path $workspaceRoot 'release\release_notes.md'
Get-FileHash -Algorithm SHA256 $bundle
gh release create $tag $bundle -R $repo --target $sourceCommit --prerelease --title $tag --notes-file $releaseNotes
gh release view $tag -R $repo
```

发布后再用 `ARTIFACTS.md` 的下载步骤从空目录取回。若没有 Release 上传权限，先核对账号是否已接受协作者邀请以及仓库权限；仍不行就记录 `BLOCKED`，不要把模型只留在自己的硬盘上宣称交付。

在该轮 `report/` 中提交机器可读的 `model_delivery_<任务编号>.json` 或等价清单，至少写明：

| 字段 | 必填内容 |
| --- | --- |
| 身份 | 任务编号、候选版本、源提交完整 SHA、适用阶段、状态（电脑上限 / 可部署候选 / 板上已验证） |
| 资产 | 私有 Release URL/标签、每个附件名、字节数、SHA-256、解包后的必要文件清单与各文件 SHA-256 |
| 获取 | 另一台电脑从 GitHub 下载、校验、解包的命令；所需仓库权限和工具版本；超大文件的分卷重组办法；存储总目录与大型缓存位置 |
| 运行 | 依赖锁定、入口命令、模型加载步骤、输入/输出采样率/声道/位宽、重采样和归一化规则、目标条件加载方式、输出位置 |
| 证据 | 数据切分与素材 SHA、客观指标、对照基线、测试命令、模型参数量/磁盘大小/MAC 或 FLOP、推理耗时与峰值内存、失败案例 |
| 板端边界 | 因果/未来上下文、预计缓冲与端到端延迟、Cortex-A9/1 GB DDR 可行性、量化或 PL 算子计划；哪些只是估计、哪些已经板测 |

报告不能只给一个权重文件名或绝对路径。提供一条从**干净检出目录和空模型目录**启动的完整推理命令，以及一个非锁定验收集的短 WAV 烟雾测试；说明正常输出应满足的基本条件（例如非空、采样率/时长合理），不能把目标留出 Track 9 泄漏进训练或选参。包和命令必须能在另一台 Windows 电脑上按文档重建运行；需要 Linux 或特定驱动时明确写出环境和替代路径。

## 发布前必须自测

1. 把任务分支推到 GitHub，并用本私有仓库的 Release 上传完整模型包。正式报告和 `coummucation.md` 同时写入标签、附件、SHA-256、源提交及取回命令。
2. 在同一项目总目录下新建**空的 `receive-check/` 子目录**重新检出对应提交；在不读取原训练目录、`build/generated/`、本机隐含缓存的条件下，用仓库权限下载 Release 附件，逐件比较字节数和 SHA-256，再解包核对必要文件。
3. 在这个干净目录按所记录的依赖安装及推理命令运行短 WAV 烟雾测试，确认程序确实加载所下载的权重，产出可播放的转换 WAV，并记录命令、环境、退出码、输出格式与运行时间。把原始终端证据或小型 JSON/TXT 摘要提交 `report/`。
4. 只有上述取回和运行成功、且 `plan.md` 的客观门通过后，才可标记 `WAIT_LOCAL_TEST` 交给 Hardware-A/B。若音质门未过，按 `REJECTED` 保存失败证据；若无法上传、下载或缺依赖，标记 `BLOCKED`。远端不得自行标记真人试听、Cortex-A9、PL 或实时通过。

## 板卡方接收步骤

Hardware-A/B 从报告中的 PR/提交和 Release 标签获取**同一版本**的代码与模型，先在自己的电脑独立下载并核对 SHA-256，再运行相同短 WAV 推理。取回成功才进入 Cortex-A9 文件转换、用户试听与后续 PL/实时验收；任一差异都回填到 `coummucation.md`。在 PR 尚未合并时需显式检出候选分支或提交；只看 `main` 可能读不到新代码或交付清单。合并后可从 `main` 读取清单，但权重仍要从对应 Release 下载。
