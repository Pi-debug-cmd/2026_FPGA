## 0. 先更正一条我上轮的错误结论

上一份报告（`board_c_20261025_stage2.md` 第 5.3 节）说"实时整链的瓶颈是**内存带宽**，所以 int8 是正解"。**这个判断经实测是错的**，先更正：

| 实验 | 权重流量 | MLP 段耗时 |
|---|---|---|
| fp32，8 帧/批 | 57 MB/s | 1,865 ms |
| fp32，4 帧/批（流量 ×2） | 115 MB/s | 2,097 ms |
| **int8，8 帧/批（流量 ÷4）** | **14 MB/s** | **1,656 ms** |

4 帧→8 帧把流量减半，耗时降 11%（2,097→1,865）；int8 再减 4 倍流量，耗时又只降 11%（1,865→1,656）。**流量减 4 倍只换来 11%，说明 MLP 是"发射/指令受限"（issue-bound），不是带宽受限。**

原因是内核算过：每个权重是标量（沿 reduction 维度 i），必须 `vdup` 成向量再 `vmlal.s16`/`vmlaq_f32`，所以 int8 与 fp32 的**指令数几乎一样**（每 8 个 MAC 约 3 条 vs 2.7 条），int8 省的是字节不是指令。A9 的 NEON 是 64 位、128 位运算占 2 周期，理论上限 ~2 MAC/cycle，实测 ~0.7 MAC/cycle，差距在发射与停顿，不在 DDR。

**所以 int8 不是实时链路的解药**（下面第 3 节的 underrun 数据也证实：int8 之后仍然 underrun）。

## 1. int8 后四项指标（验收：UTMOS 降 ≤0.10、身份降 ≤0.01、CER 不涨）

## 3. 延迟 vs underrun 帕累托表（供你选）

延迟定义：一个块的**首样本**从被采集到被写出 = `B`（攒块）+ `proc(B)`（该块处理耗时）。这是本设计的结构性下限。

| 块长 B | proc/块 | 工具 RTF | **延迟 = B+proc** | 余量 B−proc | underrun/12 s | 包络相关（vs 批处理） | 峰值/削波 |
|---|---|---|---|---|---|---|---|
| 100 ms | 156 ms | **1.559** | **256 ms** | **−56 ms** | （必然更差） | 0.871 | 1.00 / 有 |
| **200 ms** | 239 ms | **1.197** | **439 ms** | **−39 ms** | **39** | 0.929 | 1.00 / 有 |
| **300 ms** | 319 ms | **1.062** | **619 ms** | **−19 ms** | **18** | 0.932 | 1.00 / 有 |
| **500 ms** | 520 ms | **1.039** | **1,020 ms** | **−19 ms** | **15** | 0.986 | 1.00 / 有 |
| 1000 ms | 976 ms | 0.976 | 1,976 ms | +24 ms | 11 | 0.992 | 0.894 / 无 |

读法：

- **余量全为负**（除 1000 ms）→ 块越小越跟不上，200 ms 时每块要 239 ms 才产出 200 ms 音频。
- 延迟 = B + proc ≈ 2B + 50 ms，所以 **≤300 ms 在本设计下不可能**：即使 B=100 ms 也有 256 ms，而且那时 RTF 1.56、质量崩到 0.871。
- **质量与延迟反着走**：100–300 ms 时逐块说话人统计不稳定，包络相关掉到 0.87–0.93，并且出现削波（峰值顶到 1.0，因为个别块增益冲高）。
- 交叉淡化 20 ms 在 B ≥ 200 ms 时是块长的 ≤10%，够用；**若真要跑 B=100 ms，应把 fade 降到 10 ms**（>10% 块长的淡化会明显吃掉块边界）。这一点已经可以用 `--fade-ms` 调。

### 关于"p95 ≤100 ms"

按实测的边际 RTF（0.95–0.97）和约 30–60 ms 的每块固定开销，要做到 100 ms 端到端：

- 需要 B ≈ 60–80 ms 且 `proc(B) ≤ 20–40 ms` → **RTF ≤ 0.3–0.5**，即整链要再快 **2–3 倍**；
- 同时 WORLD 分析本身需要一个 ~50–100 ms 的窗才能稳住 f0/包络，100 ms 以内做"块级"处理已经在算法下限附近。

**结论：p95 ≤100 ms 用当前这条 WORLD + 48 阶倒谱 + MLP 的算法链在双核 A9 上做不到**，不是常数优化问题。要达标只能换前端（例如去掉 WORLD，改成 5–10 ms hop 的轻量 STFT 包络 + 小模型），那是另一个算法选型，不是这轮的工程量。

## 4. 你提的后续三个选项，按实测逐条回答

| 选项 | 实测/判断 |
|---|---|
| 权重常驻（避免每帧重读） | 不可行：fp32 权重 4.57 MB、int8 仍有 1.14 MB，L2 只有 512 KB。而且上面证明流量不是瓶颈，常驻也换不到时间。 |
| 更大帧批（权重每 N 帧读一次） | 已测：4→8 帧只降 11%，8 帧已是最优区间（16 帧会让 16 个累加器溢出 NEON 寄存器，实测更慢）。 |
| fp16 权重 | 不可用：Cortex-A9 的 VFPv3/NEON **没有半精度算术**，只能当存储格式再转 fp32，白白多一次转换。 |

真正能提速的只剩"改算法"：WORLD 两遍合计 1.12 s（其中 D4C 已降到 0.16 s）、MLP 1.66 s（issue-bound）、STFT 0.46 s。把 WORLD 换成 STFT 包络 + 更小模型，才可能进到 RTF 0.3–0.5。

## 5. 建议的交付选择（二选一，请你定）

1. **保质量、放弃实时**：交付当前默认（fp32，RTF 0.967–0.985，四项指标全过）。演示按"离线/准离线"讲，或提前渲染好音频播放。
2. **保 int8 + 小延迟演示**：交付 `--mlp-int8`（指标不变差、权重 1.14 MB），并用 `--stream 500` 做"准实时"演示（延迟 ~1 s、15 次 underrun/12 s，需要接受咔哒声），或者用 1000 ms 块（延迟 2 s、11 次）。

int8 与 fp32 并存（`--mlp-int8` 开关），随时可切；两者共用同一份 blob，不需要重新导出权重。
