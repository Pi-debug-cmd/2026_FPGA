### 2.2 唯一设计改动：固定 ratio 常量 → AXI GPIO@0x41200000

原因不是 2018.3 兼容性，而是**任务要求“写 ratio_q16 并读回”**：仓库 v2 驱动
`src/kernel/pitch_dma_proxy.c` 与 `board/pitch_dma_control_overlay.dts` 已经约定
`0x41200000` 是双通道 AXI GPIO（ch1=ratio_q16，ch2=低有效 DSP reset），2026-10-11 的控制版
（`report/pitch_control_development_20261011.md`）就是这个结构；而 `create_audio_pitch_dma.tcl`
用的是 `xlconstant 86856`，无法读写。

`create_audio_pitch_dma.tcl` 的全部修改（4 处，变调核 RTL 一行未改）：

1. `xlconstant` → `axi_gpio:2.0`，18 位 ch1 + 1 位 ch2，全输出，
   `C_DOUT_DEFAULT = 0x15348`（上电即 86856，保持原固定比例行为）。
2. `ctrl_ic NUM_MI 6 → 7`，新增 `M06_AXI → ratio/S_AXI`，M00..M06 的 ACLK/ARESETN 循环补 M06。
3. `ratio/dout → ratio/gpio_io_o` 接 `pitch/ratio_q16`。
4. 新增 `assign_bd_address 0x41200000`。

**与 20261011 控制版的差异（如实记录）**：那版把 ch2 的 DSP_RUN 真正接到 `pitch/aresetn`（默认保持复位）；
本版为最小改动，ch2 只是可读写寄存器，`pitch/aresetn` 仍由 `crst/peripheral_aresetn` 驱动。
因此 `CONFIGURE` 的“先复位再配置”不会清空核内 2048 样本 RAM/相位；数值比对必须在**刚加载位流后的连续流**上做
（本次 M3 就是这样做的：比对前重新加载了一次位流，见 §4.1）。

## 4. M3：端到端 4 秒音频

### 4.1 方法（`src/pitch_dma_mem.c`，无内核模块）

板上没有 `pitch_dma_proxy.ko`（之前的构建产物在已消失的临时目录里，本机也没有 WSL/内核源码，
不可能在 4 小时内重建匹配 `5.15.0-xilinx` + `CONFIG_MODVERSIONS` 的模块）。因此改用**用户态 /dev/mem 直接驱动 AXI DMA**：

- 两个匿名页 → `/proc/self/pagemap` 取 PFN → `/dev/mem` 映射成**非缓存别名**，CPU 只通过该别名读写，
  DMA 看到的就是 DRAM；页表初始化产生的脏行用 ARM `cacheflush`(0x0f0002) 清 L1，再写 2 MiB 噪声把 L2 里的脏行赶回 DRAM。
- AXI DMA simple mode，每块 **1024 个 32-bit 样本（4 KiB）**，S2MM 先武装再 MM2S，轮询 `Idle` 位。
- 输入：`input_s24_stereo.raw` 的**左声道** 24 bit → PCM16（与 `src/ps/pitch_dma_stream.c` 相同的取整规则）。
- 比对：主机 `tools/compare_reference.py` 是 `axis_pitch_shift.v` 的纯整数 Python 模型
  （与 `src/reference/pitch_shift_fixed.py` 同语义），从零状态逐样本比对。

> 本设计 GPIO ch2 不接 `aresetn`，所以核内相位/RAM 不会被 `CONFIGURE` 清零。为了做“从零状态”的比对，
> 跑数前用同一个加载脚本**重新加载一次位流**（`logs/board_reload_rerun_20261025.log`），核回到 CLEAR→IDLE、RAM 全 0。

测试信号：`tools/gen_test_audio.py` 生成的 **4.000 s / 32 kHz / S24_LE / 双声道** 1,024,000 B：
180→1800 Hz 滑音 + 2/3 次谐波 + 淡入淡出 + 两段静音，左右声道幅度不同。

## 5. 遇到的问题与处理（全部保留原始日志）

### 5.1 2018.3 没有 `write_hw_platform`

`impl_2018_3.tcl` 里 `write_hw_platform -fixed -include_bit` 报：

```
write_hw_platform note: invalid command name "write_hw_platform"
```

2018.3 batch 里可用的只有 `write_hwdef` / `write_sysdef`（`info commands` 实测）。
改用 `build/export_hdf.tcl` 生成 `audio_pitch.hdf`（827,497 B）与 `audio_pitch.hwdef`：

```
# write_hwdef -force -file .../audio_pitch.hwdef
# write_sysdef -hwdef .../audio_pitch.hwdef -bitfile .../zynq_wrapper.bit -file .../audio_pitch.hdf
HDF_EXPORTED
```

2018.3 的 `.xsa` 需要 SDK/Vitis 侧 `hsi` 打包，batch Vivado 不提供；`.hdf` 是 2018.3 的等价交付物。

### 5.2 第一次建工程 GPIO 时钟未接

```
ERROR: [BD 41-758] The following clock pins are not connected to a valid clock source:
ERROR: [Common 17-39] 'validate_bd_design' failed due to earlier errors.
```

`ratio/s_axi_aclk`、`ratio/s_axi_aresetn` 没接。补上后 `AUDIO_PITCH_DMA_VALIDATED`（`logs/create3_2018_3.log`）。

### 5.3 板端 Python 没有 `mmap`

`import mmap` → `ModuleNotFoundError`。GPIO 校验改为 C（`src/gpio_check.c`）。

### 5.4 第一次端到端结果出现 2 处 8 样本全 0

首轮（未加 L2 冲刷）输出与参考有 **16 个样本**不一致（不连续的两段，每段正好 8 个样本 = 32 B），
其余全部一致。32 B 正好是 Cortex-A9 L1 cache line 大小，判断是缓冲页的**脏零行在 DMA 之后才从 L2 回写**。
ARM `cacheflush` 系统调用只清 L1，PL310 L2 未清。

修正：`memset` 2 MiB（4×L2）把脏行挤出 L2，再 `usleep(20 ms)` 等回写落地，然后才开始 DMA。
重跑后 **max diff = 0**。原始失败对照保存在 `report/m3_compare_output.txt`（FAIL，16 样本），
修正后 `report/m3_compare_clean.txt`（PASS）。

### 5.5 板端音频驱动的一次 probe 失败（不影响本任务）

## 6. 对“PL 变调替换 SoundTouch”的 RTF 预期

- 当前 SoundTouch（PS 纯软件）约 **0.05 RTF**（32 kHz 双声道实时处理占单核 5%）。
- 本 PL 路径实测：**4 s 音频 31.19 ms**，端到端 **RTF ≈ 0.0078**；其中纯 PL+DMA 只占 **≈0.0037**，
  其余是 PS 侧的 PCM16 打包/文件 I/O。实时流式集成后（去文件 I/O、零拷贝）**预期 RTF 0.004–0.008**，
  即比 SoundTouch **低 6–12 倍**的单核占用。
- 代价与限制（必须写进结论，不能吹成“零开销”）：
  1. 每 1024 样本一次 DMA 往返，实测 **118 µs**；若按 512 帧音频块处理，约 **60 µs/块**，
     即 16 ms 帧预算的 0.4%，不是瓶颈。
  2. 变调核是 **PCM16 单声道**（左声道进、双声道出），S24 输入会被截到 16 bit；
     SoundTouch 走 float/24 bit。音色对比要在同一 PCM16 前提下做。
  3. 固定比例（GPIO 可改写但需停流），没有 SoundTouch 的 tempo/pitch 独立控制。
  4. 设备树/DTS overlay 还没做：本次用 `/dev/mem` 用户态驱动验证，产品化要补
     `pitch_dma_proxy.ko`（需匹配内核的构建环境）或一个 UIO/字符设备。
