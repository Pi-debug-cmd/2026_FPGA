# O64 live 档上板实测（2026-10-27）

> 目的：确认 **O64（64 阶输出）在 `--preset live`** 下能否实时，与 T4/48 阶 live 档对比；
> 判据 **RTF ≤ 1.0 且 underrun 0**。所有数字均为本轮板端实测，原始文件在同目录
> `metrics/logs/o64_live_20261027/`。

## 0. 结论

**O64 live 可用于演示**：4 s RTF **0.860**（3 次 0.8595–0.8611），300 ms 块 60 s
**0 欠载**，p99 处理 **284.8 ms**（< 300 ms 预算）。代价是 UTMOS **2.190**（精确档 2.2659，
−0.0759），identity 反而 +0.0028。

| 项 | O64 live（本轮） | T4 live（基线） | 判定 |
|---|---|---|---|
| 4 s RTF | **0.860**（0.8602/0.8595/0.8611） | 0.845（任务书口径 0.87） | ≤1.0 ✅ |
| 300 ms 块 60 s 处理延迟 p50/p95/p99/max | **276.0 / 284.0 / 284.8 / 286.8 ms** | 268.70 / 276.70 / 277.90 / 278.10 ms | <300 ✅ |
| 端到端（+300 ms 攒块）p50/p95/p99/max | 576.0 / 584.0 / 584.8 / 586.8 ms | 568.70 / 576.70 / 577.90 / 578.10 ms | p95 ≤700 ✅ |
| 欠载（60 s / 200 块） | **0**（无一块超 300 ms） | 0 | ✅ |
| 30 min 长稳 | 见 §8 | 0 欠载 / 6000 块 | ✅ |
| 质量（23.72 s / 10 窗） | identity **0.7321** / p10 **0.7006** / 泄漏 **−0.0346** / UTMOS **2.1900** | 4 s 口径 0.6047 / — / +0.0174 / 2.1351 | UTMOS −0.076 vs 精确档 |

## 2. 命令（板端，`cd /tmp/vc`）

```sh
# 4 s RTF ×3
./vc_o64 4 native_s24 200 --preset live --model student_v5_o64.blob \
  < in.raw > /dev/null 2> live/rtf4_$i.json

# 60 s 延迟（300 ms 块，stdout 丢弃 = 纯处理口径，与 T4 基线同法）
./vc_o64 60 native_s24 200 --stream 300 --preset live --model student_v5_o64.blob \
  < /tmp/_lat15.raw > /dev/null 2> live/lat300.jsonl

# 23.72 s 整段（评分用 f32 输出）
./vc_o64 23.72 native_s24 200 --in-f32-16k --out-f32-16k --preset live \
  --model student_v5_o64.blob < male04_16k.f32 > live/o64live_full.f32 2> live/o64live_full.json
```

## 6. 四指标（`score_full.py`，与精确档同脚本同资产同口径）

先把板端 f32 转 PCM16 后按 RMS −23 dBFS 归一化（`f32_norm_wav.py` 同一 `normalise()` 规则），
再评分；与精确档的差别仅在**多了一次 PCM16 量化**（约 −96 dB，可忽略）。

| 口径（23.72 s / 10 窗） | identity_mean | identity_p10 | leakage_rel | UTMOS |
|---|---|---|---|---|
| O64 精确档（2026-10-26） | 0.7293 | 0.6919 | −0.0223 | **2.2659** |
| **O64 live 档（本轮）** | **0.7321** | **0.7006** | **−0.0346** | **2.1900** |
| Δ（live − exact） | +0.0028 | +0.0087 | −0.0123（更好） | **−0.0759** |

- CER 两档同为 5.2308（参考文本只覆盖 4 s，整段口径不可比，与 `o64_onboard_20261026.md` §7 同）；
  4 s 片段的 CER 需另测，本轮不做。
- **live 档的代价主要在 UTMOS（−0.076）**；identity/leakage 在单窗噪声内，没有退化。
- 门禁：identity/leakage 过；**UTMOS 2.190 < 2.30**，与精确档一样未过，差距在模型能力。

## 8. 30 min 长稳（300 ms 块，`--preset live`）

运行方式与 T4 基线完全相同（`stab30.sh` 的 O64 变体：4 s 输入循环 450 份 → `vc_o64 --stream 300
--preset live` → `aplay`），从 07:25:14 连续跑到 07:55:14。

| 指标 | 值 |
|---|---|
| 块数 / 音频时长 | **6000/6000 块**（1800.0 s），block 序号 1..6000 连续、**0 个缺口** |
| 流水线退出码 | rc=0（`STAB_DONE`） |
| **aplay 欠载** | **0**（`aplay.log` 无 underrun 行） |
| RSS | **8,408 KB 恒定**（t=30 s→1770 s，Δ=0；t=0 为 5,472 KB 是 blob 尚未触碰；瞬态最大 9,196 KB） |
| 空闲内存 | 619,928 → 615,212 KB（缓慢下降，无泄漏特征） |
| 削波 | **10,501 样本**（T4 同口径为 21,473） |
| 30 min 汇总 | `proc_ms` 1,793,863、wall 1,799,831.7 ms、**rtf 0.9966** |

> **口径说明（重要）**：30 min 这条链里 `aplay` 在管道下游，`vc_o64` 的 stdout 会被反压，
> 所以遥测里的 `proc_ms` 含"等 aplay 消费"的时间，`rtf 0.9966` 是**消费节奏**而不是纯计算 RTF
> （T4 同链路是 0.9963、proc 均值 298.9 ms，O64 是 0.9966、298.98 ms——两者都由 aplay 定速）。
> 纯计算口径看 §4 的 60 s / stdout→/dev/null：p50 276.0 / p99 284.8 ms。
> 30 min 里 `proc` p95 374 ms 同样是反压造成的排队，不代表处理超时；判据以 **aplay underrun = 0** 为准。

**判定**：O64 live 30 min 0 欠载、0 掉块、RSS 恒定，满足"RTF ≤1.0 + underrun 0"，
**可用于演示**；回退仍是 `/tmp/vc/vc_live` + `student_v5.blob`（T4/48 阶，未改动）。
