## 2. 权重导出

`host/app/export_weights.py` 本来就是按 ckpt 头导出的（`out_dim = ck["nceps_out"]`），
O64 ckpt 的 `nceps_out=64`、`dct_out=(64,513)`，所以**不需要改导出脚本的输出维度**，
只要指对 ckpt。导出元数据（`student_v5_o64.json`）：

```
bytes 4941804  sha256 01aecb78d4a5a9b1a960f4a15cbc4bc524e005a39e59a54b107a5ebc2f32bbc5
in_dim 646  hidden 512  layers 4  out_dim 64  context 4  nceps_in 32  n_bins 513
params 1152064  pitch_ratio 1.4
dct_out_orthonormality_maxerr 1.19e-06   synth_vs_dct_out_maxerr 3.7e-09
```

`pitch_ratio` 取 1.4：O64 ckpt 里写的是 1.35，但**T4 的 ckpt 也是 1.35，而板端一直用
1.4 且与电脑端 1.4 链路对齐**；这里沿用 1.4 以保持与 T4/参考渲染同一条链路
（O64.wav 用的也是 SoundTouch 30/10/10 + 1.40063×）。

## 3. C 侧改动（`host/app/src/vc_stream.cpp`）

排查结论：**运行时没有硬编码 48 的数组**——`out_dim / nceps_out` 全部从 blob 头读，
`res`、`synth_T`、`c48`、int8 的 `qWout` 都是按 `m.out_dim` 动态分配的。因此不需要
"48→64 改数组尺寸"，实际改动只有两处：

1. 注释里 4 处写死的 “48” 改成 `out_dim`（头文件数据流、synth_T 布局、`res`、反 DCT）。
2. `main()` 里加输出阶数契约（`host/app/src/vc_stream.cpp`，load_model 之后）：

```cpp
if (model.out_dim != model.nceps_out)
  die("blob out_dim %d != nceps_out %d", model.out_dim, model.nceps_out);
if (model.out_dim % kMlpJB != 0)
  die("blob out_dim %d is not a multiple of kMlpJB=%d", model.out_dim, kMlpJB);
```

理由：MLP 微内核每次出 `kMlpJB=4` 个神经元，64 与 48 都能整除；这个断言把
"blob 头声明的阶数必须能被内核铺满" 变成加载期错误，而不是等到越界写。
`mlp_int8.inc` 的输出层同样按 `m.out_dim` 循环（64 % 4 == 0），int8 路径无需改动。

## 7. 验证

### ① 板端输出 vs Python O64 参考（4 s）

Python 参考：`ref_port.py --ckpt O64.pt --in-f32 dump/x16.f32 --xB-f32 dump/xb16.f32`
（用 C 的 x16/xB 喂进去，把变调实现差异从比对里剔除，这是工程里原有的做法）。

| 对比 | corr | SNR | max_abs_diff |
|---|---|---|---|
| **板端 y16 vs Python O64 参考 y16** | **0.999999987** | **75.71 dB** | 5.88e-04 |
| 板端 x16 vs x86 x16（前置检查） | 1.000000000 | ∞（逐位相同） | 0 |

阈值 0.999 / 40 dB，两项都过。75.7 dB 的残差来自 WORLD 实现版本
（板端 third_party/world 4.2 vs Python 的 pyworld 0.3.5）：单看 `logsp`
这一级就已经是 76.32 dB，属于算法实现级差异，不是移植错误。

### ② 四指标（`score_full.py`，与电脑端同脚本同资产）

先把 f32 按与参考 `O64.wav` 相同的规则归一化（RMS −23 dBFS），再评分
（`score_root/` 里是**字节未改的** `score_full.py` + `evaluator.py`，
只把损坏的 manifest 换成等价的干净副本——原 manifest 因历史编码问题已不是合法
JSON，`json.loads` 直接报 invalid escape）。

| 口径 | identity_mean | identity_p10 | UTMOS | leakage_rel |
|---|---|---|---|---|
| 电脑端 O64.wav（23.72 s，参考） | 0.7195 | 0.6653 | 2.2681 | −0.0219 |
| **板端 O64（23.72 s 整段）** | **0.7293** | **0.6919** | **2.2659** | **−0.0223** |
| 差 | +0.0098 | +0.0266 | −0.0022 | −0.0004 |
| 电脑端 O64（同 4 s 片段，Python 参考） | 0.5862 | — | 2.2253 | +0.0493 |
| **板端 O64（同 4 s 片段）** | **0.5860** | — | **2.2260** | +0.0479 |

- 整段口径：identity 0.7293 落在 **0.72±0.01** 内，UTMOS 2.2659 落在 **2.27±0.05** 内 ✅
- 同输入口径：板端与 Python 参考几乎逐位一致（Δidentity 0.0002、ΔUTMOS 0.0007、
  CER 0.1538 完全相同）✅
- 4 s 片段只有 0.586 是**片段本身的统计量导致的**（电脑端同片段 0.5862），不是板端问题
- CER：4 s 片段 0.1538（2/13 字错，电脑端同片段同为 0.1538）。整段 23.72 s 的 CER
  不具可比性（参考文本只有 4 s，脚本输出 5.23），与参考 O64.wav 的 5.31 一样是
  "分母错配"，不参与判定。

## 10. 限制与后续

1. O64 的 `--ap-stride 1` 精确档 rtf = 1.35（4 s 用 5.4 s），**不能直接当 live 档用**，
   所以本报告把 O64 记为**质量定版**，不是实时交付档。
   要上实时必须先接受隔帧近似（`--preset live` 那种），那会改变音色指标，
   需要另一轮测量——本次没有做，也不该把"上板成功"说成"实时可用"。
2. 电脑端 O64 的 0.7195 是 **10 窗平均**；单窗（4 s）噪声约 ±0.02，
   所以 0.7293 vs 0.7195 的 +0.0098 仍在单窗噪声内。
3. 整段上板用了 `--in-f32-16k`（跳过 127 抽头重采样），因为这轮只验证模型链；
   32 kHz S24 全链路的等价性由 4 s 那一轮（走完整重采样）证明。

## 11. 2026-10-27 补测：O64 的 live 档（推翻 §10 第 1 条的"未测"状态）

O64 + `--preset live` 已在同一块板上实测（完整数据见
[`../metrics/O64_LIVE_20261027.md`](../metrics/O64_LIVE_20261027.md)）：

- 4 s RTF **0.860**（3 次 0.8595–0.8611）；300 ms 块 60 s 处理 p99 **284.8 ms**、**0 欠载**；
  30 min **6000/6000 块、0 aplay 欠载、0 掉块、RSS 8,408 KB 恒定** → **可用于演示**。
- 质量代价：23.72 s / 10 窗 UTMOS **2.1900**（精确档 2.2659，−0.0759）、identity **0.7321**（+0.0028）、
  leakage **−0.0346**（更好）。
- 因此演示定版改为 **O64 + live 档**；§3–§7 的精确档数字仍是**质量上限口径**，两者不要混读。
