# 04 数值对齐与上板：从"74.86 dB 好像还行"到"16 个样本为什么是 0"

日期：2026-10-25
相关：`board_c_20261025.md` §8.2、`pl_build_20261025.md` §5.4、
`pl_vocoder_feasibility_20261025/FEASIBILITY.md` §6、`fpga/report/m3_compare_output.txt`

## 1. 这一轮要解决什么

两条线同时要"和参考实现逐样本对齐"：

- **PS 侧**：C 实现 vs Python oracle（WORLD/特征/MLP/包络/ISTFT 全链）。
- **PL 侧**：RTL 变调核 vs 定点 Python 模型（128000 样本）。

## 2. 提示词要点

> "每一级中间量都要能 dump 出来单独比，不要只比最终波形。给出每级的 max|Δ|、相对 RMS、
> 相关系数。**如果某一级对不上，先证明是输入不同还是代码不同**。"

## 3. 关键决策

| 决策 | 依据 |
|---|---|
| 逐阶段 dump（f0 / logsp / ap / 68 维特征 / 句级统计 / 归一化输入 / MLP 残差 / 包络 / 增益 / mask / xB / 最终波形） | 只有这样才能定位到"哪一层" |
| C 侧加 `--in-f32-16k` / `--xB-f32` 测试钩子，让 C 与 oracle 吃**逐字节相同**的输入 | 否则永远分不清"代码差异"和"dump 下来的 float32 舍入" |
| DMA 比对前重新加载一次位流 | 本设计 GPIO ch2 没接 `aresetn`，核内 RAM 不会被 `CONFIGURE` 清零 |

## 4. 被证伪的假设与纠正过程

### 4.1 "板端输出 vs oracle 只有 74.86 dB，说明 C 实现有 bug"

- **当时判断**：74.86 dB 远低于其它级的 121–139 dB，怀疑实现差异。
- **证伪方法**：把 C 也喂 oracle 用的那份 **float32 dump**（`--in-f32-16k` + `--xB-f32`），
  而不是让 C 内部用自己的 double 中间量。
- **结果**：同一条对比从 74.86 dB 升到 **126.16 dB** `[实测]`。
- **纠正**：74.86 dB 不是代码差异，而是"输入差 1 ulp"经过 4 层 512 的 GELU 网络放大约 10³ 倍。
  **这类"放大"必须由"喂同一份输入"来排除**，不能靠看代码。
- **沉淀**：任何跨实现比对，第一条纪律是**输入必须逐字节同一份**。

### 4.2 "只有 16 个样本不对，而且是 0，应该是 RTL 复位没清干净"

- **当时判断**：16 = 2 × 8，像是两处复位残留。
- **关键观察**（真正定位的一步）：错的**形状**是"两段、每段正好 8 个样本、值全 0、
  起点 32 B 对齐"，而且**第二次运行不复现**。
- **实验**：只加 `cacheflush()`（ARM 私有 syscall）→ 仍然错；
  再加 **2 MiB（4×L2）内存冲刷 + `usleep(20 ms)`** → `max_abs_diff = 0` `[实测]`。
- **纠正**：是 **L2 脏零行在 DMA 之后回写**覆盖了 DMA 输出，不是 RTL。
  ARM 的 `cacheflush` 只清 L1，PL310 L2 不归它管。
- **沉淀**：详细判读表见 `skill/dma_cache_coherency/diag_checklist.md` §1。
  一句话：**先算清楚"错的形状"，再读代码。**

### 4.3 "127 抽头重采样器的群延迟不重要，比对时对齐一下就行"

- **当时判断**：`(127−1)/2 = 63` 个 32 kHz 样本 = 31.5 个 16 kHz 样本，
  非整数也就是"差半样本"，做相关对齐能吸收。
- **证伪**：对齐后 SNR 只有 46.8 dB（而其它级是 120+ dB）。
- **纠正**：把抽取起点改成 `off=1`，让群延迟变成**整数 31 个样本** → 对齐质量恢复 `[实测]`。
- **沉淀**：多速率系统里，**群延迟必须是整数个输出样本**，否则所有逐样本比对都不可信。

### 4.4 "查表只要取最近的整数点就够了"（前人 RTL，本次复核时确认）

- **现象**：复数 exp 单元 `49248/49248` bin **全部失配**（96 次调用 × 513 bin）。
- **根因**：cos/sin 查表漏了 `frac` 线性插值。最小复现（报告给出的 bin1）：
  `a=0.09486, b=−0.04470, J=1016, F=47617`：
  - 正确：`e·LUT_sin[1016] + 0.7266·(LUT_sin[1017] − LUT_sin[1016]) → −6429`
  - 错误：`e·LUT_sin[1016] → −7071`
  - 而 `143940 × (−6439)/131072 = −7071` —— 这个等式就是"只用 LUT[j]"的指纹。
- **纠正**：查表输出只要参与相乘，就必须插值，且插值权重必须与地址**同源**。
- **沉淀**：这类错误在波形上不像"错拍"，只像"精度不够"，**极难肉眼定位**；
  必须靠"每个 bin 都错且误差同号"这个形状去判。

### 4.5 "98% 的样本都对，应该可以直接交付"（对 74.86 dB 那次的教训）

- 最终交付口径定成两级：**vs 定点模型 = 0 LSB（严格）** + **vs 浮点黄金 ≤ 2 LSB**。
  只跑行为级仿真不算通过，必须**后综合 funcsim** + 板端 PCM hash 比对。
- 这条写进了 `skill/golden_reference_compare/report_template.md` 的门禁栏。

## 5. 沉淀

1. **输入同一份 → 才允许讨论代码差异**（4.1）。
2. **错的形状 → 指向根因**，形状包括：长度、对齐、是否全 0、是否只在首轮、误差符号（4.2/4.4）。
3. **多速率先对齐整数群延迟**（4.3）。
4. **验收口径分层**：严格层证明"实现与模型一致"，宽松层证明"与浮点黄金等价"（4.5）。
5. **失败产物要留档**：`m3_compare_output.txt`（FAIL）和 `m3_compare_clean.txt`（PASS）
   一起交付，比只交 PASS 更有说服力。
