# 03 性能优化：一个被自己推翻的"带宽瓶颈"，和猜错两次的 MLP

日期：2026-10-25
相关：`board_c_20261025_int8_latency.md`（§0 是公开的自我更正）、`board_c_20261025_stage2.md` §2.1/§3

## 1. 这一轮要解决什么

RTF 2.067（4 s 音频 8269 ms）要压到 ≤1.0。分阶段耗时显示
MLP 3817 ms（0.95）、D4C 1470 ms（0.37）、CheapTrick 1234 ms（0.31）。

## 2. 提示词要点

## 3. 被证伪的假设（按发生顺序，含原话级结论）

### 3.1 假设一：MLP 是内存带宽受限，所以 int8 权重是解药 —— **错**

- **当时判断**（写进了 stage-2 报告的 §5.3）："实时整链的瓶颈是内存带宽与 DMA 争用，
  所以 int8 是正解。"
- **证伪实验**：只改"每批帧数"与"权重精度"，量权重流量与 MLP 耗时：

| 实验 | 权重流量 | MLP 段耗时 |
|---|---|---|
| fp32，8 帧/批 | 57 MB/s | 1865 ms |
| fp32，4 帧/批（流量 ×2） | 115 MB/s | 2097 ms |
| **int8，8 帧/批（流量 ÷4）** | **14 MB/s** | **1656 ms** |

- **判读**：流量 ÷4 只换来 **11%** 提速；如果真是带宽受限，应该是接近 ÷4 的收益。
- **纠正后的判断**：MLP 是**指令发射受限（issue-bound）**。原因是内核里每个权重是标量，
  必须先 `vdup` 成向量再 `vmlal.s16`/`vmlaq_f32`，int8 与 fp32 的**指令数几乎相同**
  （每 8 个 MAC 约 3 条 vs 2.7 条）。A9 的 NEON 是 64 位、128 位运算占 2 周期，
  实测只有 ~0.7 MAC/cycle，差距在发射与停顿，不在 DDR。
- **影响**：int8 从"实时链路的解药"降级为"权重 4.57 MB → 1.14 MB、指标不降"的可选开关。
  真正的提速来自**寄存器分块 + 显式 NEON + 双核**。

### 3.2 假设二：MLP 逐帧推理是"算力"问题 —— 错

- **当时判断**：24 ms/帧太慢，应该批处理提吞吐。
- **证伪**：批处理反而更慢（激活块 32 KB 反复冲刷 L1）。
- **纠正**：是**内存层级**问题（权重 4.6 MB/帧，每帧全读一遍），
  解法是 2 维分块（8 帧 × 8 神经元，激活块 16 KB 落在 L1）→ 9.5 ms/帧 `[实测]`。

### 3.3 假设三：再加帧批（8 → 16）能继续线性收益 —— 错

- **结果**：16 帧时 16 个累加器溢出 NEON 寄存器组，**实测更慢** `[实测]`。
- **纠正**：8 帧已是最优区间。

### 3.4 假设四：fp16 权重能省一半带宽 —— 不成立

- **事实**：Cortex-A9 的 VFPv3/NEON **没有半精度算术**，fp16 只能当存储格式再转 fp32，
  白白多一次转换 `[推断，架构手册]`。

### 3.5 假设五：整包 `-O3` 会更快 —— 错

- **结果**：主机 553 ms（-O3）vs 539 ms（-O2），反而更慢；输出逐字节相同 `[实测]`。
- **纠正**：只用 `-O2`，只对 `mlp_forward_batch` 加 `optimize("O3")` 属性。

## 4. 最终真正有效的四项（全部 `[实测]`）

| 优化 | 收益 | 质量代价 |
|---|---|---|
| D4C 每 10 帧 + 插值 | −1315 ms | 相关 0.99975 / UTMOS −0.0018 |
| 第二遍 WORLD 藏到 MLP 后面（线程） | −900 ms（几乎完全隐藏） | 0 |
| MLP 寄存器分块 + 显式 NEON + 双核 | 2097 → 1272 ms | 0（与串行 corr 1.000000000） |
| STFT/ISTFT 单精度 FFT + 重采样抽头对称折叠 | −518+−51 ms | `max|Δ|=0` |

结果：4 s 8269 → 3857–3941 ms，**RTF 0.967 / 0.983 / 0.985（三次）**。

## 5. 仍然没做到的部分（不掩饰）

- **500 ms 块做不到 0 欠载**：每块 480 ms vs 500 ms 预算，余量 20 ms（4%），
  调度抖动必掉一次。已试 2/3/4 s 的 start-delay，无改善。
- **`p95 ≤ 100 ms` 用这条算法链做不到**：需要 B≈60–80 ms 且 proc≤20–40 ms，
  即整链再快 2–3 倍；这要换前端（去 WORLD、改 5–10 ms hop 的轻量 STFT），是另一个算法选型。
- **300 ms 块 0 欠载是刀刃上的**：L5 档每块 285 ms（aplay 链路均值），余量 15 ms（5%）。
  2026-10-26 做了 30 min 长稳：**0 欠载**（6000 块），但每块分布是双峰的
  （纯处理 p50 268.7 ms，aplay 链路 p95 373.9 ms，靠 aplay 2 s 缓冲吸收），
  平均 rtf 0.9963——余量仍然只有 1.1 ms/块，不能说"很宽裕"。

## 6. 沉淀

1. **"流量减 4 倍只快 11%" 这种反直觉结果，比任何 profiler 都好用**：
   它一句话就把"带宽受限"排除掉了。设计实验时要优先找这种**单变量、强对比**的量。
2. **公开更正比悄悄改好**：`board_c_20261025_int8_latency.md` §0 原文写着"先更正一条我上轮的错误结论"。
   这不是丢分项，这是**可信度**。
3. **优化要按"有没有质量代价"排序**：跳过计算 > 并行隐藏 > 近似。
4. **参数不是越多越好**：`--ap-stride 20` 让 UTMOS 更好（2.1157）但 identity 掉 0.0117
   （超过 0.01 门限），所以停在 10 —— "某一项变好"不等于"可以采纳"。
